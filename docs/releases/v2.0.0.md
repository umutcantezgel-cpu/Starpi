# Starpi v2.0.0

Starpi is a knowledge assistant in the browser that shows how far each answer can be trusted. It
answers from your files and a shared knowledge base, cites every passage, compares every statement
of the answer with the passages it cites, and gives you a receipt that anyone can check against the
original files. This release makes the check see what it was blind to (a statement that keeps the
source's words and reverses their meaning, a name in the wrong place, a value attached to the
wrong thing), makes receipts tamper-evident and signable, and brings the check into CI.

**Try it:** [www.starpi.app](https://www.starpi.app): click *Try with sample files*, ask a
suggested question, open the *Source check* and the *Receipt*. No account or API key needed.
**Use the checks in your app or CI:**
[`@starpi/core`](https://github.com/umutcantezgel-cpu/Starpi/tree/v2.0.0/packages/core#readme)

## Highlights

- **Source check version 2**, in English and German, deterministic, without a second model:
  - *Reversed negations* (`negation_inversion`): "Power over Ethernet is supported" against "… is
    not supported", "erlaubt" against "verboten", also through un-, in- and dis- words. Negations
    written differently ("no longer", "neither … nor", "darf … nicht") are read by their meaning;
    "not … until", "only after", ranges and questions are not reversals.
  - *Names in the wrong place* (`name_context`): "Marcus Hale owns the specification" when the
    excerpt says Priya Raman owns it and Marcus Hale maintains the network.
  - *Values next to something else*, now read from the passage around each value, without the
    section heading; version numbers ("firmware 4.2.1") are compared as codes.
  - Every new reason is **weak**: a statement is listed for review with the passage that says
    otherwise, never marked unsupported by these rules. Version 1 of the rules can still be run
    (`groundAnswer(…, { version: 1 })`), byte for byte, and recomputes receipts of 1.x.
- **Measured once on answers held out from development**
  ([results](https://github.com/umutcantezgel-cpu/Starpi/blob/v2.0.0/docs/eval/v2-results.md)):
  version 2 detects 17 of 23 wrong names (version 1: 10), 20 of 24 values attached to the wrong
  thing (13) and 16 of 23 reversed statements (0), and marks no statement of a faithful answer
  unsupported in any set. The targets of 8 of 10 are reached for values, not for names (74 %) or
  negations (70 %); faithful statements marked weak rise from 4 to 8 of 144 in that set. The
  [protocol](https://github.com/umutcantezgel-cpu/Starpi/blob/v2.0.0/docs/eval/v2-protocol.md)
  froze the held-out set by SHA-256 before the first rule was written, and records a red-team
  review that made the negation check weak-only before the measurement.
- **Receipts v2** (`starpi.receipt/v2`): an RFC 6962 Merkle tree over the citations with an
  inclusion proof per citation, so one cited passage can be shown with its proof without the
  others; optional Ed25519 or ECDSA P-256 signatures with WebCrypto; `starpi-verify-receipt
  --public-key` and the receipt dialog check them. v1 receipts are still read and verified.
- **`starpi-ground` for CI:** checks release notes, documentation or any Markdown document
  against source files and writes text, JSON or SARIF 2.1.0 (validated against the OASIS schema),
  so a pull request shows an unsupported statement in GitHub code scanning. A five-line Actions
  snippet is in the READMEs.

## Breaking changes

- Receipts are written as `starpi.receipt/v2`; verifiers of 1.x refuse them.
  `buildReceipt(draft, { schema: RECEIPT_SCHEMA_V1 })` still writes v1, and v1 receipts are still
  read and verified.
- The source check runs `starpi-grounding` 2 by default, so verdicts change; `{ version: 1 }`
  runs the rules of 1.x.
- Two new reason codes, `negation_inversion` and `name_context`, appear in reports, receipts,
  the JSON Schema and SARIF.

Checked by hand for this release:

- The packed tarball installs into an empty project; every example in both READMEs and in the
  receipt specification was run against it, and it type-checks in a strict TypeScript consumer
  without `skipLibCheck`.
- SARIF from `starpi-ground` validates against the OASIS SARIF 2.1.0 schema; both SBOMs pass the
  CycloneDX 1.5 schema and are byte-identical across two runs.
- Before the final measurement, two reviews (a red team with 843 faithful paraphrases and a code
  review) found faithful statements marked unsupported, a date-shaped version read two ways, a
  regular expression with quadratic run time and order-dependent name checks; all were fixed and
  are covered by tests ([protocol](https://github.com/umutcantezgel-cpu/Starpi/blob/v2.0.0/docs/eval/v2-protocol.md#review-before-the-final-measurement)).
  A security review of receipts, signatures and both commands (forged and reordered citations,
  key substitution, algorithm confusion, private keys and `__proto__` in receipts, terminal escape
  sequences in file names and statements) found no defect.
- At the check's limits (300 statements, 200,000 characters of excerpts) version 2 takes about
  twice as long as version 1 (2.8 to 3.4 s against 1.3 to 1.7 s on a 4-vCPU container).

`npm audit --omit=dev` and `pip-audit` report no known vulnerabilities (2026-10-14). The full
`npm audit` still reports GHSA-vfj7-8cjw-p6xm (braces 3.0.3, no patched release) in the file
watcher of Tailwind CSS 3, development tooling that is not shipped in `dist/`. actionlint,
zizmor (pedantic) and gitleaks report nothing.

## Upgrade notes

- **`@starpi/core`:** code that switches over reason codes needs the two new ones; code that
  reads receipts needs to accept `starpi.receipt/v2` (or write v1 with `RECEIPT_SCHEMA_V1`).
  `GROUNDING_VERSIONS` and `REASON_CODES` are exported. PDF extraction still needs the optional
  peer `pdfjs-dist` 6.
- **CI:** `npx --yes --package=@starpi/core@2 starpi-ground --answer docs/notes.md --source docs
  --format sarif --output starpi.sarif`, then `github/codeql-action/upload-sarif`; see the
  [package README](https://github.com/umutcantezgel-cpu/Starpi/blob/v2.0.0/packages/core/README.md#check-documents-in-ci).
- **Database and backend:** no migration and no change.
